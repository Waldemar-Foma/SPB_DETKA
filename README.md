# Сервис подбора исполнителей

Сервис для заказчика: создать заявку → описать потребность или загрузить ТЗ → получить TOP-5 подходящих контрагентов → сравнить их на карте/в списке → выбрать исполнителя → получить контакты → завершить заказ → оставить отзыв.

Проект рассчитан на локальный запуск через Docker Desktop.

---

## 1. Что умеет система

### Для заказчика
- регистрация и вход;
- экран **«Мои заявки»**;
- создание новой заявки вручную или из ТЗ;
- интеллектуальный подбор контрагентов;
- TOP-5 кандидатов;
- режимы **«Карта»** и **«Список»**;
- фильтрация по типу компании;
- краткие метрики по каждому кандидату;
- объяснение простыми словами, почему компания подходит;
- выбор исполнителя;
- раскрытие контактов после выбора;
- сохранение заявки на дашборде;
- завершение заказа;
- отзыв 1–5 после завершения;
- удаление заявки;
- автоматический архив старых заявок;
- отдельная проверка контрагента и просмотр внутренних отзывов.

После выбора исполнителя вернуться к подбору для этой заявки нельзя. То же касается завершённых, архивных и удалённых заявок.

---

## 2. Как работает подбор

Подбор состоит из нескольких этапов.

### Этап 1 — первичный семантический поиск
Используется связка:

- `all-minilm`
- FAISS

Текст заявки превращается в embedding, после чего FAISS быстро находит семантически похожих контрагентов.

### Этап 2 — финальное ранжирование
Кандидаты пересчитываются с учётом:

- смыслового совпадения;
- ОКПД2;
- релевантного опыта;
- количества участий;
- количества побед;
- win rate;
- отзывов внутри сервиса;
- географии и логистического смысла;
- текущей нагрузки по активным заявкам сервиса.

После этого формируется итоговый **TOP-5**.

### Этап 3 — объяснение
`qwen2.5:3b` не выбирает исполнителя.

Она получает уже рассчитанные факты и пишет понятное объяснение для заказчика: сильные стороны, опыт, статистика, логистика и возможные нюансы.

Если Qwen недоступна, используется rule-based fallback — сайт продолжает работать.

### Дополнительная модель E5
`multilingual-e5-base` используется как дополнительный семантический сигнал финального ранжирования.

## 3. Требования

Нужно установить:

1. **Docker Desktop**
2. Windows 10/11
3. Желательно не менее 16 ГБ RAM
4. Интернет для первого запуска — Docker должен скачать образы и локальные AI-модели

Python, Flask, Playwright, FAISS и остальные Python-библиотеки вручную ставить не нужно: они устанавливаются внутри Docker-контейнера.

## 5. Какие файлы обязательны

### Обязательно оставить

#### `START.bat`
Точка входа для запуска проекта в Windows.

Он вызывает `START.ps1`, поэтому **START.ps1 тоже обязателен**.

#### `START.ps1`
Основной launcher: проверяет Docker, подготавливает запуск и поднимает контейнеры.

#### `docker-compose.yml`
Основная Docker-конфигурация:

- Flask-приложение;
- Ollama;
- Qwen;
- all-minilm;
- volumes;
- порты;
- переменные окружения.

#### `docker-compose.e5.yml`
Дополнительный compose-файл для `multilingual-e5-base`.

Пока E5 используется проектом, файл нужен.

#### `Dockerfile`
Собирает контейнер Flask-приложения и устанавливает Python-зависимости и Chromium для Playwright.

#### `docker-entrypoint.sh`
Запускается внутри контейнера приложения.

Он:
- проверяет наличие REAL-базы;
- при необходимости импортирует реальный датасет;
- иначе создаёт DEMO;
- затем запускает Flask.

#### `.dockerignore`
Нужен, чтобы огромные модели, ZIP, база и временные файлы не попадали в Docker build context.

#### `requirements.txt`
Основные зависимости приложения:

- Flask;
- SQLAlchemy;
- requests;
- pypdf;
- python-docx;
- numpy;
- FAISS;
- pytest.

#### `requirements-data.txt`
Зависимости импорта и обогащения данных:

- pandas;
- openpyxl;
- Playwright.

**Не удалять**, пока Dockerfile устанавливает оба файла отдельно.

#### `app.py`
Главная точка создания Flask-приложения.

#### `config.py`
Конфигурация Flask, SQLite, cookies и сессий.

#### `backend/`
Вся серверная бизнес-логика.

#### `scripts/`
Импорт реального датасета, обогащение и сервисные скрипты.

#### `templates/`
HTML-шаблоны.

#### `static/`
CSS, JavaScript и frontend-ресурсы.

#### `ml_artifacts/`
FAISS-индекс и сопоставление индекса с ИНН.

Без этой папки основной ML-поиск через FAISS работать не будет.

#### `models/`
Здесь хранится GGUF E5.

#### `instance/`
Здесь находится локальная SQLite-база и маркер готовой REAL-базы.

**Не удаляйте**, если не хотите импортировать реальные данные заново.

## 6. Что можно удалить

### `CHECK_PROJECT.bat`
Не нужен для обычного запуска.

Он нужен только для проверки проекта:
- compileall;
- pytest;
- JS syntax check.

Если места/чистота важнее — можно удалить.

### `seed.py`
Можно удалить **только если DEMO-режим вообще больше не нужен**.

Сейчас `docker-entrypoint.sh` вызывает `seed.py`, когда реальный датасет отсутствует. Поэтому для универсальной сборки лучше оставить.

### Старые README и инструкции
Если этот файл используется как единый README, можно удалить:

```text
LAUNCH_GUIDE.md
DOCKER_GUIDE.md
MODEL_INTEGRATION.md
V9_CHANGES.md
V10_CHANGES.md
V11_CHANGES.md
V12_CHANGES.md
```

Они не нужны приложению для работы.

### Материалы для защиты
Также можно убрать из рабочей сборки, если они уже не нужны:

```text
HACKATHON_PITCH.md
DATASET_AUDIT.md
```

На работу сайта они не влияют.

### Кэши и временные файлы
Безопасно удалить:

```text
__pycache__/
*.pyc
.pytest_cache/
.venv/
```

---

## 7. Что нельзя удалять просто так

### Не удаляйте `requirements-data.txt`
Dockerfile прямо устанавливает:

```text
requirements.txt
requirements-data.txt
```

Если хотите оставить только один requirements-файл — сначала нужно объединить зависимости и изменить Dockerfile.

### Не удаляйте `docker-compose.e5.yml`
`START.ps1` и `CHECK_PROJECT.bat` могут подключать его автоматически при наличии E5 GGUF.

Сначала нужно перенести сервис `e5` в основной `docker-compose.yml` и изменить launcher.

### Не удаляйте `instance/`, если REAL-база уже импортирована
Иначе при следующем запуске придётся повторно разбирать исходный большой датасет.

### Не удаляйте `ml_artifacts/`
Иначе FAISS-подбор перестанет работать и система будет уходить в fallback.

# 8. Первый запуск с реальными данными

Рекомендуемая структура:

```text
hackathon/
├── RLT.Uni_СПБ_1-2_10_2026.zip
└── project/
    └── START.bat
```

1. Запустите **Docker Desktop**.
2. Дождитесь, пока Docker Engine полностью загрузится.
3. Запустите:

```bat
START.bat
```

Первый запуск может занять продолжительное время.

Docker может:

- скачать Python image;
- скачать Ollama;
- скачать llama.cpp server;
- скачать `qwen2.5:3b`;
- скачать `all-minilm`;
- подготовить E5;
- собрать app image;
- импортировать большие CSV в SQLite.

После первого успешного импорта следующие старты значительно быстрее.

Приложение:

```text
http://127.0.0.1:5000
```

Страница входа:

```text
http://127.0.0.1:5000/auth/login
```

## 9. REAL и DEMO

### REAL
Если проект видит реальный датасет, `docker-entrypoint.sh` запускает импорт.

После успешного импорта создаётся:

```text
instance/REAL_DATA_READY
```

При следующих запусках база не пересобирается.

### DEMO
Если реального датасета нет и локальной базы ещё нет, выполняется:

```bash
python seed.py
```

и создаётся демонстрационная база.

## 10. Пользовательский сценарий

### 1. Авторизация
Без входа рабочие страницы недоступны.

### 2. Мои заявки
После входа заказчик попадает на экран своих заявок.

Даже если заявки уже существуют, кнопка **«Создать заявку»** остаётся доступной.

### 3. Создание
Два варианта:

- загрузить ТЗ;
- описать заказ вручную.

### 4. Подбор
Система анализирует заявку и показывает TOP-5.

Доступны:

- карта;
- список;
- фильтр типа компании;
- метрики;
- отзывы;
- краткое объяснение.

### 5. Выбор
Заказчик самостоятельно нажимает **«Выбрать исполнителя»**.

После этого:

- выбор фиксируется;
- подбор для этой заявки блокируется;
- раскрываются контакты;
- заявка остаётся в «Моих заявках».

### 6. Завершение
После фактического выполнения заказа заказчик помечает заявку завершённой.

### 7. Отзыв
Только после завершения можно поставить оценку 1–5 и оставить подробный отзыв.

Отзывы участвуют в последующих рекомендациях и видны в разделе проверки контрагента.

## 12. AI-компоненты

### all-minilm
Используется для embedding текста заявки перед FAISS-поиском.

Запускается через Ollama.

### FAISS
Использует готовый индекс поставщиков и формирует первичный пул кандидатов.

### multilingual-e5-base
Дополнительный semantic scoring.

Запускается через llama.cpp server.

Модель:

```text
models/multilingual-e5-base-q4_k.gguf
```

### Qwen 2.5 3B
Используется только для объяснения уже рассчитанного результата.

Qwen не должна самостоятельно:
- назначать победителя;
- придумывать опыт;
- придумывать отзывы;
- придумывать контакты;
- придумывать логистические факты.

---

## 13. Если AI-модель недоступна

Сервис не должен полностью падать.

Предусмотрены fallback-механизмы:

- если FAISS/all-minilm недоступны — DB/keyword prefilter;
- если E5 недоступна — ranking работает без E5;
- если Qwen недоступна — используется rule-based объяснение.

Состояние моделей можно проверить в админ-панели.
